# QQ 合并转发占位符问题归档（2026-08-19）

## 一、问题现象

在**私聊合并转发（信封）**中，腾讯服务器返回的消息内层参与者可能出现 **QQ 号和用户名均为占位符** 的情况：

```
user_id = 1094950020
sender.user_id = 1094950020
sender.nickname = "QQ用户"
```

- 占位符 QQ 号：**1094950020**（固定值，非真实用户号）
- 占位符昵称：**"QQ用户"**（腾讯默认显示名）
- **关键危害**：同一个占位符 `1094950020` 在不同信封中可能代表**不同的真实用户**；且与真实用户的 QQ 号（如 3541215132）在数据中并存，极易混淆。

## 四、为什么部分信封未被污染

同一批转发内容若在**多个信封**中出现（重复转发），先入库的版本以**真实 sender.user_id** 入库（message_id 去重，INSERT OR IGNORE 跳过后续重复）；只有 sender.user_id 本身即占位符的消息才会以 1094950020 入库。

## 五、处理规范（以后遇到占位符必须遵守）

1. **不要直接映射占位符**：`1094950020` 不是固定用户，先列出所有涉及的信封（forwards 表按 `envelope_time` 分组），与用户确认每个窗口的真实归属。
2. **区分"入库时身份"**：messages 表中 `peer_id=1094950020` 的行，`user_id` 可能是真实号（439161815/2956792638/3541215132 等）也可能是占位符——**只改 `user_id=1094950020` 的行**，别碰真实号行。
3. **按 message_id 定位**：用信封 content_raw 中的 `real_id` 集合精确 UPDATE，不要按 user_id 全量替换。
4. **先备份再修改**：修改前 `Copy-Item data/qqchat.db data/qqchat.db.bak-<时间戳>`。
5. **修改后验证**：统计各用户消息数、检查占位符剩余行数为 0、窗口 id 归属无串号。
